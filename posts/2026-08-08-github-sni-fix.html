国内直连 GitHub 的正确姿势：一次 SNI 投毒排查

2026-08-08 · 网络排障 · GitHub / SNI / SSH

上一篇《WorkBuddy 网络故障排查记》解决的是 MTU 黑洞；这一篇记录另一个独立的问题：git clone / push 频繁失败，时灵时不灵。两者都是网络层故障，但机制完全不同，诊断手法也值得对照。

一、故障矩阵

先把现象按目标主机拆开，规律立刻浮现：

目标现象
git clone/push（github.com HTTPS）间歇性失败：21s 连接超时 / SSL_ERROR_SYSCALL / connection reset，重试几次又能成
gh CLI（api.github.com）基本稳定
GitHub Pages（*.github.io）0.1 秒内被连接重置，几乎必挂
raw.githubusercontent.com超时

「同一台机器、同一时间，不同 GitHub 域名命运迥异」——这说明不是本机问题，而是针对特定目标的干扰。

二、逐层排查

1. DNS 有没有被污染？

用阿里 DoH（https://223.5.5.5/resolve）与本机 DNS 交叉比对：github.com、api.github.com、raw.githubusercontent.com 返回的都是 GitHub 真实 IP 段（20.205.x / 140.82.x / 185.199.x），DNS 是干净的。

2. IP 可达性批量探测

对所有候选 IP 做 TCP 443 探测，结果是「分裂」的：

20.205.243.166  TIMEOUT   ← github.com DNS 唯一返回的 IP，恰好被封
20.205.243.165  TCP_OK    ← 同一网段隔壁的 IP 却是通的
140.82.112.3    TCP_OK 274ms
140.82.113.4    TCP_OK 1278ms
192.30.255.116  TIMEOUT   ← 老 IP 段已全灭

DNS 只给了一个 IP，而这个 IP 恰好被墙 —— 这就是「时通不通」的表层原因之一。

3. TCP 通 ≠ 能用

对 TCP 可达的 IP 做真实 TLS 握手测试，更诡异的一幕出现了：

--- round 1 ---
140.82.112.3  github.com  TLS_OK 1122ms   ← 能握手！
140.82.114.4  github.com  TLS_OK 548ms
--- round 2 ---
140.82.112.3  github.com  TIMEOUT          ← 同样的 IP，全灭
140.82.114.4  github.com  TIMEOUT
--- round 3 --- 依旧全灭

TCP 三次握手能过、TLS ClientHello 一发出去就被丢/重置，而且成功过一次之后会进入一段「投毒窗口」，后续连接全部失败 —— 这是典型的 TLS SNI 关键词过滤：审查设备读取 ClientHello 里的域名（SNI），命中规则就注入 RST 或丢包。

验证：强制 TLS 1.2 重试（排除版本指纹因素）—— 照样被重置。干扰与 TLS 版本无关，只认域名。

4. 找一条不被过滤的通道

继续探测两个特殊目标：

140.82.121.5  api.github.com   TLS_OK ×3 轮全通过   ← API 域名不在过滤名单
20.205.243.160:443  →  "SSH-2.0-7f27de7" ×3 轮全通过 ← SSH 通道畅通！

ssh.github.com:443 是 GitHub 官方支持的「SSH over HTTPS 端口」入口。SSH 握手没有 TLS ClientHello、没有 SNI 指纹，因此完全不触发过滤。

三、最终方案

git 操作全部改走 SSH over 443，三步完成：

# 1. 生成密钥（我放在 D 盘，不占 C 盘）
ssh-keygen -t ed25519 -f "D:/Study/qoder/ssh/id_ed25519_github"

# 2. 上传公钥（或网页 Settings → SSH keys）
gh ssh-key add "D:/Study/qoder/ssh/id_ed25519_github.pub"

# 3. git 全局指定密钥，仓库 remote 改用 SSH-over-443 URL
git config --global core.sshCommand \
  "ssh -i D:/Study/qoder/ssh/id_ed25519_github -o IdentitiesOnly=yes"
git remote set-url origin "ssh://git@ssh.github.com:443/用户名/仓库名.git"

改完后 git ls-remote / push 一次通过，不再需要重试循环。gh CLI 走的 api.github.com 本就稳定，再往 hosts 里固定一条实测可达的 IP 防止 DNS 抽风即可。

四、解决不了的部分

诚实记录：github.com 网页和 GitHub Pages 的 HTTPS 访问依然被 SNI 投毒，hosts 改 IP 无效（过滤认域名不认 IP）。这部分要彻底解决只能上代理类工具（Watt Toolkit、dev-sidecar 之类），或换个网络环境访问。git 工作流不受影响，对我来说已经够用。

五、经验

  • 按目标主机拆分现象是第一招：同机不同域名命运不同，立刻指向「针对性干扰」而非本机故障；
  • TCP 通 ≠ TLS 通 ≠ HTTP 通，三层要分别测；「握手成功一次后连续失败」是 SNI 投毒窗口期的指纹；
  • 强制 TLS 1.2 对照实验可以快速排除「版本指纹」假设；
  • GitHub 官方留了 ssh.github.com:443 后门，是国内直连做 git 操作最稳的免费方案 —— 没有 SNI，就没有伤害；
  • 与上篇 MTU 黑洞对照：那是「大包被丢、小包能过」，认包大小；这是「特定域名被重置」，认 SNI。同一条线路上可以同时存在多种互不相干的故障，诊断时不要先入为主。

—— 探测脚本见文末思路：DoH 交叉解析 + TCP/TLS 批量探测 + SSH banner 探测，每个环节都是几十行 Node.js。
