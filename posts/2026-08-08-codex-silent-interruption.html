消失的工具调用：Codex 会话「中断」悬疑排查

2026-08-08 约 11 分钟 排障实录 · 第三弹

前两篇排查的都是网络层；这一篇换口味——AI 智能体自己的「灵异事件」。Codex CLI 在跑长任务时反复出现同一种怪象：每次它说完「接下来我要做 X」、正准备执行下一步动作时，会话就戛然而止。没有报错、没有超时提示，就像被人拔了线。这次不靠猜，用四层日志交叉取证加三轮受控复现，把嫌疑一个个排除。

一、链路结构与故障现象

先交代这条请求链路，后面的证据都挂在上面：

chain · overview
Codex CLI 0.147 (Responses API, wire_api=responses, store=false)
    ↓  http://127.0.0.1:15721/v1
cc-switch 3.19 本地代理（Responses → chat/completions 转换、重试×6、熔断）
    ↓  https
海外中继站（转发到模型服务）

用户视角的现象极其稳定：「每次在你准备进行下一步动作时就会停止」。而且专挑长会话下手，短对话没事。

二、两种完全不同的「中断」

把 cc-switch 日志按时间轴铺开，第一类问题立刻现形——但注意时间窗：全部集中在 17:00 之前：

时间事件性质
16:35:09上游 HTTP 504 Gateway Time-out（FWD-003）硬失败
16:55–16:58连续 503「服务繁忙」风暴，codex 方向 31 条 FWD-003硬失败
17:55 之后FWD-003 归零，但「中断」仍在继续网络无罪

503/504 是中继站过载，cc-switch 有 6 次重试加熔断器兜底，属于「疼但能自愈」。真正折磨人的是 17:00 之后的第二类：日志里一片祥和的静默中断。

三、取证：四处日志现场

1. 客户端错误日志——全是烟雾弹

Codex 自己的日志数据库里有 60 条 ERROR，时间戳与中断时刻完全吻合。逐条抓出来一看：全部是 PowerShell 工具执行失败（沙箱权限拒绝、引号解析错误），没有一条流断开记录。中断在客户端侧是静默发生的。

2. 会话回放——抓到现行

解析 rollout 会话文件（.jsonl）里最后一个 turn 的 SSE 事件，拿到了关键帧：

rollout · response.completed
status: completed            ← 正常完成，不是截断
incomplete_details: null     ← 没有撞输出上限
output items: [reasoning, message]   ← 只有推理和一段话，没有 function_call
usage: input=121142  cached=118784   ← 上下文已膨胀到 12 万 token
推理段尾部: "Let me query the sqlite database…"   ← 明明白白写着要动手
实际输出: 一段「接下来我要查询……」的叙述，然后 turn 结束

模型想执行工具调用（推理里都写好了），但响应里只有叙述、没有动作。HTTP 200、状态 completed、usage 正常——从协议角度看，这是一次「成功」的请求。

四、受控复现：给链路做无罪推定

「工具调用在传输中丢失」是最大嫌疑。设计三轮受控实验，每轮只留一个变量：

实验条件结果
A · 直连中继 vs 经代理小上下文 + tools 数组，两条链路对照finish=tool_calls，双双正常
B · 推理档位xhigh 最高推理档重测工具调用完整返回
C · 超大上下文构造 128,400 token 输入（超过故障会话的 121k），原样走代理 /responses11.8 秒返回 [reasoning, function_call]，零丢失
repro · big-context result
HTTP 200  first byte 10974ms
output item types: ["reasoning","function_call"]
status: completed   incomplete_details: undefined
usage: {"input_tokens":128400,"output_tokens":57}
TOOL_CALL_PRESENT name=shell args={"command":["ls","-la"]}

三轮全绿。转换层、中继、模型在 12 万 token 级别都能正确投递工具调用。链路无罪，剩下的嫌疑人只有两个：沙箱和模型自己。

五、真凶落网

真凶之一：沙箱权限墙

回放里那些「PowerShell ERROR」不是烟雾弹，是案发现场：Codex 的 workspace-write 沙箱只放行工作区目录（在 C 盘），而我的规则是所有产出必须落 D 盘。于是每一次写文件尝试都撞上 UnauthorizedAccessException，模型被权限墙反复弹回，最终学会了「描述动作但不执行」——turn 就此终结。

真凶之二：叙述惯性

一旦前几个 turn 以「只说不做」收尾，长会话的上下文就把这个模式固化成惯性：推理里计划得好好的，输出却只剩旁白。这也解释了为什么短会话从不复发——没有累积的坏样本。

六、修复清单

四个改动全部落在 ~/.codex/config.toml：

config.toml · diff
# 1. 沙箱放行 D 盘工作区（拆掉权限墙）
[sandbox_workspace_write]
network_access = true
writable_roots = ["D:\\Docs\\qoder", "D:\\workspace"]

# 2. 行动纪律指令（打断叙述惯性）
instructions = """
ACTION DISCIPLINE (critical):
- Never end a turn by merely announcing what you are about to do.
  If you state an intended action, you MUST issue the corresponding
  tool call in the SAME turn.
- When blocked by a permission/sandbox error, do not stop: report the
  exact blocker, then immediately try an alternative path.
...
"""

# 3. 上下文卫生（12 万 token 的教训）
model_auto_compact_token_limit = 160000

# 4. 删除失效旧键 disable_response_storage
#    新版对非 Azure 端点已无条件 store=false（client.rs 实锤），
#    留着只会让 --strict-config 报错

顺带挖出一个彩蛋：官方文档链接已全部改指新站且拒绝抓取，于是直接反查 298MB 的原生二进制字符串表加 gh api 拉源码，确认了每个配置键的真实拼写——文档会过期，二进制不会说谎。

七、验证与一个意外的发现

修复后用 codex exec --strict-config 跑真实任务：创建文件到 D 盘 → 读回比对，一次通过（此前必撞权限墙）：

verify · codex exec
Step 1 done: created D:\Docs\qoder\codex-tools\verify-out\sandbox-write-test.txt
Step 2 read content: [CODEX_SANDBOX_FIX_OK_20260808]
VERIFY: PASS - content identical

排查收尾时还撞上一桩案中案：工作目录 D:\Study 整个「失踪」，追查发现它早在前一天深夜就已被改名成 D:\Docs。更精彩的是，故障会话的 rollout 里留着它 18:19 的内心独白——「沙箱可写根是 C:\Users\28169……先试试，不行就提权」——提权成功后在 D:\Docs 里留下了一个空的 codex_diag_test 目录。撞墙、绕路、留痕，正是上文诊断的行为模式的完整切片。

八、经验

  • 「静默中断」先查响应体再查网络：response.completed 里 status=completed 却没有 function_call，说明请求成功了，是内容层面的问题，别在超时重试上浪费精力；
  • 受控复现是终审：小上下文、推理档位、超大上下文三轮对照全绿，才能给链路判无罪，把矛头对准真正的行为层原因；
  • 权限墙会驯化模型：反复的 UnauthorizedAccessException 不只是报错，它会把「只叙述不执行」写进上下文惯性——沙箱白名单要和用户的文件规则对齐；
  • 长会话记得开自动 compact（model_auto_compact_token_limit），上下文窗口大不代表质量不衰减；
  • 配置键拿不准时，--strict-config 是最快的校验器；官方文档抓不到就查二进制字符串表和源码，两条路都比猜快。
